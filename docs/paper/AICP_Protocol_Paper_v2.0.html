1. Abstract

The rapid proliferation of autonomous AI agents — systems capable of independently discovering services, negotiating terms, and executing transactions — has exposed a critical infrastructure gap. While protocols such as the Model Context Protocol (MCP), Agent-to-Agent (A2A), and Agent Communication Protocol (ACP) address tool integration and inter-agent messaging, none provides the foundational layer that every autonomous agent requires: verifiable identity anchored to a responsible human or organization, decentralized service discovery, standardized onboarding, and provider-agnostic payment capabilities.

The Agentic Identity and Commerce Protocol (AICP) fills this gap with a four-layer protocol stack built on W3C Decentralized Identifiers (DIDs), Verifiable Credentials (VCs), a custom Agent Name System (ANS), a four-phase onboarding state machine, and a cryptographic payment token framework supporting Stripe, PayPal, and USDC. AICP operates as complementary infrastructure — it does not replace MCP, A2A, or ACP, but provides the identity and commerce substrate they lack.

This paper presents the complete technical specification, architecture, and reference implementation of AICP v1.0. The protocol is implemented as a production-grade Go server backed by PostgreSQL and Redis, with client SDKs in TypeScript and Python, a Kubernetes operator for consortium ledger management, and comprehensive deployment tooling via Helm charts, Grafana dashboards, and Prometheus observability. All components are open source under the Apache 2.0 license.

2. Introduction & Motivation

The AI ecosystem is evolving from isolated model inference toward networks of autonomous agents that perform real-world tasks: booking travel, managing cloud infrastructure, executing financial transactions, and coordinating with other agents. This evolution demands infrastructure that the current landscape does not provide.

2.1 The Agent Autonomy Gap

Today's AI agents operate in a fragmented environment. Each service provider implements bespoke authentication, proprietary onboarding flows, and siloed payment mechanisms. An agent that needs to interact with ten services must navigate ten different identity systems, ten onboarding processes, and ten payment integrations. This fragmentation creates several critical problems:

  • No verifiable identity: Agents cannot prove who they are or who authorized them. API keys are bearer tokens with no cryptographic binding to a responsible entity.
  • No accountability chain: When an agent performs a harmful action, there is no standardized way to trace it back to the human or organization that deployed it.
  • No discovery mechanism: Agents cannot programmatically find services that match their capabilities. Discovery relies on hardcoded URLs or human-curated directories.
  • No universal onboarding: Every service implements its own registration flow. An agent cannot autonomously sign up for a new service without custom integration code.
  • No payment abstraction: Agents lack a standardized way to authorize, execute, and verify payments across different providers and currencies.

2.2 Why Existing Protocols Are Insufficient

The emerging agent protocol landscape addresses parts of this problem but leaves the foundational layers unaddressed:

  • Model Context Protocol (MCP) by Anthropic standardizes how agents access tools and context through a structured interface. However, MCP assumes the agent already has identity, already has access, and already has payment capability. It is a tool-use protocol, not an identity or commerce protocol.
  • Agent-to-Agent (A2A) by Google defines how agents communicate and delegate tasks to each other. A2A handles agent-to-agent messaging but does not address how an agent proves its identity to a service, how it gets onboarded, or how it pays for access.
  • Agent Communication Protocol (ACP) focuses on multi-agent orchestration and workflow coordination. Like A2A, it operates at the communication layer and assumes identity and payment are solved elsewhere.

AICP's Position: AICP is not a competitor to MCP, A2A, or ACP. It is the infrastructure layer beneath them. An agent uses AICP to establish identity, discover services, onboard, and set up payment — then uses MCP to access tools, A2A to coordinate with other agents, and ACP for multi-agent workflows. AICP provides the "plumbing" that makes autonomous agent operation possible.

2.3 Design Goals

AICP is designed around six core principles:

  1. Principal Accountability: Every agent action traces to a verified human or organization through cryptographic delegation chains.
  2. Agent Autonomy: Within delegated boundaries, agents operate independently — discovering services, negotiating terms, and executing transactions without human intervention.
  3. Provider Agnosticism: The protocol abstracts over payment providers (Stripe, PayPal, USDC), identity methods, and deployment platforms.
  4. Protocol Complementarity: AICP integrates with existing agent protocols rather than replacing them.
  5. Decentralized Trust: A consortium ledger with multi-validator consensus eliminates single points of failure and vendor lock-in.
  6. Production Readiness: Every protocol component has a reference implementation that is deployable, observable, and scalable.

3. Problem Statement

Consider a concrete scenario: an AI assistant agent needs to autonomously purchase cloud compute from a provider it has never interacted with before. Today, this requires:

  1. A human to manually create an account on the cloud provider's website.
  2. A human to enter payment information and agree to terms of service.
  3. A human to generate API credentials and configure them in the agent.
  4. Custom integration code for that specific provider's API.
  5. Manual monitoring of spending and credential rotation.

With AICP, this becomes a five-call automated flow: 

// 1. Agent discovers the compute service via ANS
const service = await agent.discover("cloud-compute");

// 2. Agent initiates onboarding (presents DID + credentials)
const session = await agent.onboard(service.did);

// 3. Capabilities are negotiated (compute tier, rate limits)
await session.negotiate({ tier: "standard", capabilities: ["vm.create"] });

// 4. Payment is authorized (delegation credential scopes spending)
await session.authorize({ paymentMethod: "stripe" });

// 5. Account is provisioned (agent receives service credentials)
const account = await session.provision();

The agent never leaves the protocol. Identity verification, trust assessment, capability negotiation, payment authorization, and account provisioning all happen through standardized AICP endpoints. The human principal who deployed the agent defined the spending limits, allowed service categories, and trust thresholds in advance through delegation credentials.

4. Protocol Architecture

AICP is organized as a four-layer protocol stack, where each layer builds on the capabilities of the layer below it. Cross-cutting concerns — the consortium ledger, trust framework, and event system — span all layers.

Figure 1: AICP Four-Layer Protocol Stack with Cross-Cutting Concerns

4.1 Transport & Wire Format

AICP communicates over HTTP/1.1 and HTTP/2 with JSON as the wire format. All endpoints follow REST semantics under the base path /aicp/v1/. Real-time events are delivered over WebSocket connections authenticated via one-time tickets. Inter-validator block synchronization uses gRPC for efficient binary streaming.

All responses are wrapped in a standardized envelope:

// Success response
{
  "data": { /* payload */ },
  "meta": { "requestId": "...", "timestamp": "..." }
}

// Error response
{
  "error": {
    "code": "SPENDING_LIMIT_EXCEEDED",
    "message": "Daily spending limit of $100.00 exceeded",
    "detail": "Current daily spend: $97.50, requested: $15.00"
  }
}

4.2 Authentication

Authenticated endpoints use DID-Auth, where the caller includes an Authorization header containing a DID and an Ed25519 signature over the request. The server resolves the DID, retrieves the public key from the DID Document, and verifies the signature. This eliminates shared secrets and enables cryptographic non-repudiation.

5. Layer 1: Identity

The Identity Layer is the foundation of AICP. It provides cryptographic identity for both human/organization principals and their autonomous agents through W3C Decentralized Identifiers (DIDs) and Verifiable Credentials (VCs). Every action in the protocol traces back to a verifiable identity.

5.1 The did:aicp Method

AICP defines a custom DID method, did:aicp, with a hierarchical identifier structure that encodes the principal-agent relationship directly in the DID syntax: 

did:aicp:<principal-id>                  # Principal DID (human or organization)
did:aicp:<principal-id>:<agent-id>       # Agent DID (bound to principal)

Identifiers are derived from cryptographic keys: each ID is the base58btc encoding of the first 16 bytes of the SHA-256 hash of the entity's Ed25519 public key. This creates a compact, collision-resistant identifier that is intrinsically bound to a key pair.

Key Generation

publicKey, privateKey = Ed25519.GenerateKey()
hash = SHA-256(publicKey)
id = Base58BTC(hash[0:16])
did = "did:aicp:" + id                   // Principal
did = "did:aicp:" + principalId + ":" + id  // Agent

Security Property: Each agent has its own independent Ed25519 key pair. Compromise of an agent's private key does not compromise the principal or other agents. The principal can deactivate a compromised agent's DID without affecting the rest of the delegation tree.

Every DID resolves to a DID Document conforming to the W3C DID Core specification with AICP-specific extensions. The document contains the public keys, authentication methods, and service endpoints associated with the identity.

5.3 Verifiable Credentials

AICP uses W3C Verifiable Credentials to express capabilities, authorizations, and attestations. Three credential types are defined in the core protocol:

5.3.1 Agent Delegation Credential (AICPAgentDelegation)

Issued by a principal to an agent, this credential defines the scope of the agent's authority:

  • Delegated capabilities: What the agent is allowed to do (e.g., payment.execute, service.onboard)
  • Spending constraints: Per-transaction, daily, and monthly limits with currency
  • Service categories: Allowed merchant categories (e.g., cloud, retail)
  • Geographic restrictions: Allowed jurisdictions for transactions
  • Concurrency limits: Maximum simultaneous subscriptions

5.3.2 Spending Authorization Credential (AICPSpendingAuthorization)

Defines which payment methods the agent can use and under what conditions:

  • Payment methods: References to configured payment adapters
  • Spending limits: Per-transaction, daily, and monthly caps
  • Merchant categories: Allowed categories for spending
  • Approval threshold: Amounts above this trigger principal approval workflow

5.3.3 Attestation Credential (AICPServiceAttestation)

Issued by services to agents after successful onboarding, serving as proof of established relationship. These contribute to the agent's trust score and can be presented during future onboarding with other services.

5.4 Credential Revocation

AICP implements RevocationList2020 for efficient credential status checking. Each issuer maintains a compressed bitstring where each bit position corresponds to a credential. Revocation is a single bit flip, and verifiers check the bit at the credential's revocationListIndex. The list uses a default capacity of 131,072 entries (217) with atomic updates and version tracking.

Revocation events are broadcast in real-time via the WebSocket event system (credential.revoked) and anchored in the consortium ledger for auditability.

5.5 Delegation Chain Verification

When a service receives a request from an agent, it verifies the complete delegation chain:

  1. Resolve the agent's DID Document from the ledger
  2. Extract the aicp:principal field to identify the controlling principal
  3. Retrieve the delegation credential referenced in aicp:delegationCredential
  4. Verify the credential's signature (issued by the principal's key)
  5. Check that the credential is not expired or revoked
  6. Validate that the requested action falls within the credential's delegated capabilities
  7. Confirm spending constraints are satisfied

This chain provides cryptographic accountability: every agent action can be traced through an unforgeable chain of signatures to the responsible principal.

5.6 Multi-DID Method Resolution

While did:aicp is the native method, the protocol supports resolving multiple DID methods through a pluggable Strategy pattern. A MultiMethodResolver inspects the DID method prefix and delegates to the appropriate resolver:

  • did:aicp: Resolved from the consortium ledger (native method)
  • did:key: Stateless resolution — the DID Document is derived entirely from the multibase-encoded Ed25519 public key embedded in the DID itself. No network lookup required.
  • did:web: Resolved by fetching the DID Document from https://domain/.well-known/did.json (or a path-based URL for sub-paths). Enables interoperability with existing web infrastructure.

New DID methods can be added by implementing the DIDMethodResolver interface and registering with the resolver. This design ensures forward compatibility with methods like did:ion, did:peer, or future standards without modifying existing code.

5.7 Capability-Based Access Control

AICP extends delegation credentials with fine-grained, object-capability-style permissions. The CapabilityChecker supports hierarchical matching with three levels of granularity:

  • Exact match: payment:read matches only payment:read
  • Hierarchical wildcard: payment:* matches payment:read, payment:execute, payment:approve
  • Global wildcard: * matches all capabilities

For resource-scoped access, delegation credentials can include CapabilityGrant objects that bind a capability to a specific resource or service: 

{
  "capabilityGrants": [
    { "capability": "payment:execute", "resource": "svc-123" },
    { "capability": "payment:read", "resource": "*" }
  ]
}

This model follows the principle of least privilege: agents receive only the permissions they need, scoped to the resources they should access.

5.8 OpenID Connect Bridge

The OIDCBridge maps AICP DIDs to OpenID Connect-compatible identity tokens, enabling agents to authenticate with traditional web services that expect OIDC identity. This is critical for the transition period where services gradually adopt AICP alongside existing authentication systems.

The bridge issues JWS-signed ID tokens (EdDSA) containing both standard OIDC claims and AICP-specific extensions: 

{
  "iss": "https://idp.aicp.example.com",
  "sub": "did:aicp:7Vf3xPqR2nK8mY4j:9Bw2cTdR5nH7kL3p",
  "aud": "https://service.example.com",
  "exp": 1712000400,
  "iat": 1711996800,
  "aicp_did": "did:aicp:7Vf3xPqR2nK8mY4j:9Bw2cTdR5nH7kL3p",
  "aicp_did_method": "aicp",
  "aicp_principal": "did:aicp:7Vf3xPqR2nK8mY4j",
  "aicp_key_type": "Ed25519",
  "aicp_public_key_hash": "a1b2c3d4e5f6a7b8"
}

The bridge exposes standard OIDC endpoints: /.well-known/openid-configuration for discovery and /.well-known/jwks.json for key material. Services can verify AICP-issued tokens using standard OIDC libraries without any AICP-specific code.

6. Layer 2: Discovery (Agent Name System)

The Discovery Layer provides a decentralized, searchable registry for AICP-compatible services through the Agent Name System (ANS). ANS serves the same role for AI agents that DNS serves for the web — it maps human-readable names and capability queries to structured service descriptions.

Each service publishes an ANS record containing everything an agent needs to evaluate and connect to the service:

6.2 Discovery Mechanisms

AICP supports three complementary discovery mechanisms:

6.2.1 Well-Known Endpoint

Every AICP-compatible service MUST serve its ANS record at /.well-known/aicp.json. This enables direct discovery when an agent knows the service's domain — analogous to /.well-known/openid-configuration in OAuth. Responses are cached with Cache-Control: public, max-age=300.

6.2.2 Full-Text Search

The ANS registry supports full-text search via PostgreSQL's tsvector capabilities. Search queries match against service names (weight A), categories (weight B), discovery tags (weight C), and descriptions (weight D). Results are ranked by a combination of text relevance and trust score. 

GET /aicp/v1/discover/search?query=gpu+compute&limit=10&cursor=

// Returns paginated results with trust-weighted ranking

6.2.3 DID-Based Lookup

If an agent already knows a service's DID (from a referral, credential, or prior interaction), it can retrieve the ANS record directly: 

GET /aicp/v1/discover/did:aicp:8Kx2mPq4nR7tY5wJ

6.3 Trust-Weighted Ranking

Search results are not purely text-relevance ordered. The ranking algorithm incorporates the service's trust score, verification status, account age, and certification level to surface trustworthy services first. This discourages fraudulent services from gaming search results through keyword stuffing.

6.4 Federated ANS

Multiple AICP deployments can share ANS records through federated search, creating a global agent service directory without centralized control. The resolution follows a three-tier strategy:

  1. Local: Query the local ANS registry first (lowest latency, highest trust)
  2. Domain: If the agent knows the service's domain, fetch directly from /.well-known/aicp.json
  3. Federated peers: Query registered peer nodes in parallel, deduplicate results by DID, and merge with local results

Peers are registered via a thread-safe PeerRegistry that supports dynamic addition and removal of federation endpoints. Each peer has a name, endpoint URL, and optional trust weight that influences result ranking. Peer queries have independent timeouts to prevent a slow peer from blocking the entire search.

Design Note: Federated ANS uses a pull model: nodes query peers on-demand rather than replicating entire registries. This keeps the protocol simple and avoids the consistency challenges of distributed replication, while still enabling global discovery.

7. Layer 3: Onboarding

The Onboarding Layer standardizes how agents register with services through a four-phase state machine. This eliminates the need for service-specific registration code and enables agents to autonomously onboard to any AICP-compatible service.

7.1 State Machine

The onboarding flow is modeled as a deterministic finite state machine with six states and strict transition guards. Each phase represents a logical checkpoint in the registration process.

Figure 3: Four-Phase Onboarding State Machine with Failure Transitions

7.2 Phase Details

Phase 1: Initiation

The agent sends a POST /aicp/v1/onboard request with its DID, a verifiable presentation containing its delegation and spending credentials, and a list of requested capabilities. The service:

  1. Creates a Redis-backed session (24-hour TTL, auto-expires)
  2. Resolves the agent's DID and verifies the delegation chain
  3. Computes or retrieves the agent's trust score
  4. Issues a DID-Auth challenge (random nonce + domain + timestamp, 5-minute expiry)
  5. Returns the session ID and challenge to the agent

At any point during the flow, the agent can query the session state via GET /aicp/v1/onboard/{id} to check the current phase, timestamps, and any failure reason.

Phase 2: Identity Presentation

The agent responds to the DID-Auth challenge by signing it with its private key via POST /aicp/v1/onboard/{id}/negotiate. The service verifies the signature against the agent's DID Document, confirming cryptographic control of the claimed identity. If a minimum trust score guard is configured, the agent's score is checked at this phase.

Phase 3: Capability Negotiation

The service evaluates the agent's requested capabilities against its own offering and the agent's delegation constraints. It returns a set of approved capabilities and service terms including:

  • Pricing tier: Selected based on the agent's profile and negotiation
  • Rate limits: Requests per second/minute/hour
  • Billing cycle: Monthly, annual, pay-as-you-go
  • Currency: ISO 4217 code for billing

Phase 4: Payment Authorization

The agent provides a signed payment token (see Section 8) to authorize the onboarding fee or initial subscription payment via POST /aicp/v1/onboard/{id}/authorize. The service validates the token's JWS signature, checks spending limits, and processes the payment through the appropriate adapter.

Phase 5: Provisioning

Upon successful payment, POST /aicp/v1/onboard/{id}/provision finalizes the account. The service issues an attestation credential (AICPServiceAttestation) to the agent, assigns an account ID, and returns service-specific credentials. The attestation credential contributes to the agent's trust score for future interactions with other services.

7.3 Anti-Spam & Rate Limiting

The onboarding layer implements Redis-backed rate limiting to prevent abuse:

  • Per-DID rate limit: Maximum onboarding attempts per DID per time window
  • Per-IP rate limit: Prevents distributed bot attacks from the same source
  • Trust-gated access: Services can set minimum trust score thresholds, blocking unknown or low-reputation agents
  • Session limits: Maximum concurrent onboarding sessions per agent

8. Layer 4: Commerce

The Commerce Layer provides a provider-agnostic payment abstraction that enables agents to execute financial transactions within delegated boundaries. It addresses the fundamental challenge of autonomous agent commerce: how does an AI agent pay for services without holding a credit card?

8.1 Payment Token Architecture

AICP's payment mechanism is built on cryptographic payment tokens — JSON Web Signatures (JWS) using EdDSA (Ed25519) that encapsulate all payment parameters in a verifiable, tamper-proof envelope. Payment tokens are the protocol's unit of financial authorization.

Figure 4: Payment Token Lifecycle — Issuance, Execution, and Receipt

8.2 Token Structure

A payment token is a JWS (JSON Web Signature) with EdDSA algorithm containing these claims: 

{
  "jti": "pt_a1b2c3d4e5f6g7h8",           // Unique token ID (replay prevention)
  "iss": "did:aicp:8Kx2mPq4nR7tY5wJ#key-1", // Issuer (service DID + key ref)
  "sub": "did:aicp:7Vf3xPqR2nK8mY4j:9Bw2c", // Subject (agent DID)
  "aud": "did:aicp:8Kx2mPq4nR7tY5wJ",       // Audience (service DID)
  "iat": 1711929600,                          // Issued at (Unix seconds)
  "exp": 1711930500,                          // Expires (iat + 15 min)
  "aicp:payment": {
    "amount": { "value": "2500", "currency": "USD" },
    "maxAmount": { "value": "5000", "currency": "USD" },
    "purpose": "service-onboarding",
    "serviceCategory": "cloud",
    "adapterId": "stripe",
    "nonce": "f8a3b2c1d0e9f8a7b6c5d4e3",
    "idempotencyKey": "idem_x7y8z9a0b1c2d3e4"
  }
}

8.4 Payment Adapters

AICP uses the Strategy pattern for payment providers. Each adapter implements a common interface, enabling the protocol to route payments to the appropriate provider without coupling business logic to any specific payment API. 

type PaymentAdapter interface {
    Name() string
    SupportedCurrencies() []string
    Initialize(ctx context.Context, config map[string]any) error
    Healthy(ctx context.Context) error
    CreatePaymentIntent(ctx context.Context, params CreateIntentParams) (*PaymentIntent, error)
    CapturePayment(ctx context.Context, intentID string) (*PaymentCapture, error)
    RefundPayment(ctx context.Context, intentID string, params *RefundParams) (*PaymentRefund, error)
    GetPaymentStatus(ctx context.Context, intentID string) (*PaymentStatus, error)
    ValidateWebhook(ctx context.Context, payload []byte, sig string) (*WebhookEvent, error)
}

Three production adapters are implemented:

  • Stripe — Credit/debit cards, bank transfers, global coverage
  • PayPal — PayPal balance, linked bank accounts, buyer protection
  • USDC (Circle API) — Stablecoin payments, on-chain settlement, programmable money

A Sandbox adapter is also provided for testing, which simulates payment flows without connecting to external services.

8.5 Spending Controls

Spending enforcement operates at three levels:

  1. Per-transaction limit: Maximum single payment amount (from delegation credential)
  2. Daily aggregate limit: Total spending in a 24-hour window (tracked in spending_records)
  3. Monthly aggregate limit: Total spending in a calendar month

When a payment exceeds the requiresApprovalAbove threshold defined in the spending authorization credential, the system enters an approval workflow:

  1. Payment is paused and a PendingApproval record is created
  2. A payment.approval_required event is broadcast via WebSocket
  3. The principal reviews and approves/denies via POST /payment/approval/{id}/approve
  4. On approval, payment execution resumes; on denial, the payment fails with APPROVAL_DENIED

8.6 Cryptographic Receipts

Every settled payment produces a SignedPaymentReceipt containing a SHA-256 hash computed over the receipt's canonical fields (receipt ID, payer DID, payee DID, amount, timestamp). Receipts are stored in the PostgreSQL payment_receipts table and anchored in the consortium ledger as ledger entries for immutable audit. Agents can retrieve their receipt history via GET /payment/status/{id} and verify receipt integrity by recomputing the hash.

9. Consortium Ledger & Consensus

AICP anchors all critical state — DID documents, credential status, payment receipts — in a consortium ledger. Unlike public blockchains, AICP's ledger is a permissioned, append-only log maintained by a set of known validators. This provides the immutability and auditability of a blockchain without the throughput limitations and energy costs.

9.1 Ledger Architecture

Figure 5: Consortium Ledger — Block Chain, Pending Entry Pool, and Validator Quorum

9.2 Block Structure

Each block contains:

  • Block number: Monotonically increasing sequence
  • Previous hash: SHA-256 of preceding block (chain integrity)
  • Merkle root: Root of Merkle tree computed over all entry hashes in the block
  • Entry count: Number of ledger entries included
  • Validator DID: The proposing validator (round-robin leader)
  • Validator signature: Proposer's Ed25519 signature over the block hash
  • Collected signatures: Array of validator signatures (minimum 2f+1 for finalization)

The block hash is computed as: SHA-256("number:previousHash:merkleRoot:proposerDID"), providing a deterministic, verifiable fingerprint.

9.3 Consensus Protocol

AICP uses a simplified permissioned consensus with the following properties:

  1. Leader election: Round-robin based on block number: leader = validators[blockNumber % len(validators)]
  2. Block proposal: The leader batches pending entries, computes the Merkle root, and proposes the block
  3. Signature collection: The leader requests signatures from all validators in parallel via gRPC
  4. Finalization: Once 2f+1 signatures are collected (where f = floor((n-1)/3)), the block is finalized and stored
  5. Block sync: Non-leader validators pull finalized blocks via gRPC streaming to maintain consistency

Single-Node Mode: For development and small deployments, AICP supports single-validator operation where the local node is always the leader and only its own signature is required. This enables zero-configuration local development while maintaining the same block structure.

The ledger is backed by PostgreSQL 16+ with the following core tables:

  • ledger_blocks — Block chain with hash links and validator signatures (JSONB)
  • ledger_entries — Individual entries with block foreign key (NULL for pending)
  • did_documents — Current DID document state with JSONB storage
  • did_document_versions — Full version history for auditability
  • credentials — Verifiable credentials with GIN-indexed type arrays
  • revocation_lists — Compressed bitstring revocation lists (131,072 capacity each)
  • payment_receipts — Settled receipts with unique token_jti constraint
  • used_tokens — Replay prevention table (JTI primary key)
  • spending_records — Per-agent daily/monthly spending aggregation
  • trust_scores — Computed trust scores with component breakdown

  • validators — Registered validator nodes with gRPC addresses
  • onboarding_sessions — Session state (Redis primary, PostgreSQL backup)

11.2 WebSocket Authentication

WebSocket connections use a ticket-based authentication flow to avoid passing credentials in WebSocket upgrade headers (which have limited browser support):

  1. POST /aicp/v1/ws/ticket with DID-Auth header → receives a one-time ticket (30-second TTL, stored in Redis)
  2. GET /aicp/v1/ws?ticket={ticket} → WebSocket upgrade; ticket is validated, consumed, and the connection is bound to the authenticated DID
  3. Client subscribes to event types via in-band WebSocket messages
  4. Server pushes matching events to subscribed clients

Connection parameters: 256-event buffer per client, 4KB max message size, 10-second write timeout, 60-second pong timeout, 30-second ping interval.

11.3 Event Distribution Architecture

Events flow through a three-stage pipeline:

  1. Emission: Protocol components emit typed events via the EventEmitter
  2. Distribution: Events are published to Redis pub/sub channels, enabling horizontal scaling across multiple server instances
  3. Delivery: The WebSocket Hub receives events from Redis and routes them to subscribed clients based on event type and DID

This architecture enables AICP servers to scale horizontally — a client connected to Server A will receive events emitted by Server B, because both share the same Redis pub/sub backbone.

12. Security Considerations

Security is foundational to AICP, not an afterthought. The protocol's design addresses the unique threat model of autonomous agents operating in adversarial environments.

12.1 Threat Model

ThreatMitigation
Agent key compromiseIndependent Ed25519 keys per agent; principal can deactivate compromised agent DID without affecting others. Revocation broadcast via WebSocket events.
Payment replay attacksAtomic double-spend prevention: the MarkTokenUsed operation uses a PostgreSQL INSERT with unique constraint on jti — concurrent duplicate requests fail atomically (error code 23505), eliminating TOCTOU race conditions. Supplemented by nonce in Redis cache and idempotencyKey at the payment adapter level.

ImpersonationDID-Auth requires Ed25519 signature over each request; no shared secrets or bearer tokens. Challenge-response uses crypto/subtle.ConstantTimeCompare to prevent timing attacks.
Unauthorized spendingThree-tier spending limits (per-transaction, daily, monthly) enforced atomically — the CheckAndRecordSpending operation combines limit verification and recording in a single PostgreSQL CTE with FOR UPDATE row locking, preventing concurrent overspend. High-value transactions trigger principal approval workflow with 15-minute TTL.
Credential forgeryAll credentials are JWS-signed by the issuer; verification checks signature, expiry, and revocation status.
Ledger tamperingAppend-only blocks with RFC 6962-compliant Merkle trees (0x00 leaf prefix, 0x01 branch prefix for domain separation) and 2f+1 validator signatures. Block hash chain prevents retroactive modification.
Man-in-the-middleAll transport over TLS. DID-Auth signatures provide end-to-end integrity independent of transport security.
Information leakageError responses sanitized via ProtocolErrorResponse — internal errors return generic "an internal error occurred", never exposing database details, stack traces, or file paths.
SSRF / Federation abuseDomain validation rejects path traversal and special characters. Federation peer responses capped at 1 MiB via io.LimitReader.
WebSocket auth bypassWebSocket upgrade requires TicketAuth configuration — returns 503 when unconfigured rather than silently allowing unauthenticated connections.
Denial of serviceRedis-backed rate limiting per DID and per IP. Trust score gating for onboarding. Session limits prevent resource exhaustion. Request body size capped at 1 MB.
Validator collusion2f+1 quorum requirement means at least two-thirds of validators must agree. Validator set managed by consortium governance.

12.2 Cryptographic Choices

  • Ed25519: All signing operations use Ed25519 via Go's stdlib crypto/ed25519 (server), @noble/ed25519 (TypeScript SDK), and PyNaCl (Python SDK). Ed25519 provides 128-bit security, deterministic signatures, and fast verification.
  • SHA-256: Used for document hashes, Merkle trees (with RFC 6962 domain separation), DID generation (truncated), block hashes, and receipt hashes.
  • JWS/EdDSA: Payment tokens use JSON Web Signature with EdDSA algorithm via go-jose/v4. Algorithm allowlisting enforces EdDSA only — no algorithm confusion attacks.
  • Constant-time comparison: All security-critical comparisons (challenge-response verification) use crypto/subtle.ConstantTimeCompare to prevent timing side-channel attacks.
  • Base58btc: Multibase encoding for public keys and signatures (compact, no ambiguous characters).

All cryptographic primitives use audited, maintained libraries with no custom implementations. The Go server's crypto is FIPS-capable through the standard library.

12.3 Privacy

AICP minimizes personally identifiable information (PII) in the protocol:

  • DIDs are pseudonymous — they reveal the principal-agent relationship but not the principal's real-world identity
  • Trust scores are computed from on-chain behavior, not off-chain personal data
  • Payment receipts contain DIDs and amounts but no personal payment details (those are in the adapter layer)
  • The protocol supports selective disclosure through Verifiable Presentations — agents reveal only the claims needed for a specific interaction

13.6 MCP Server Integration

The CLI includes a built-in Model Context Protocol (MCP) server that exposes AICP operations as MCP tools, enabling AI agents and LLMs to interact with AICP services through the standardized MCP tool-calling interface. The server uses JSON-RPC 2.0 over stdio transport: 

aicp mcp   # Start MCP server over stdio

The server registers 16 tools covering the full AICP lifecycle:

Each tool acts as a thin adapter between MCP tool calls and the AICP REST API: it validates input parameters, constructs the HTTP request, forwards it to the AICP server, and returns the JSON response formatted for LLM consumption. This means any MCP-compatible agent framework (Claude, GPT, or custom agents) can discover services, onboard, and make payments through AICP without any AICP-specific client library.

Complementary by design: The MCP server materializes the "AICP + MCP" complementary model described in Section 14. An LLM uses MCP to call AICP tools, which in turn provide the identity and commerce infrastructure that MCP assumes but does not implement.

15. Future Work & Roadmap

15.1 Implemented Extensions (v2.0)

The following items from the original roadmap have been implemented in the reference implementation and are documented in their respective sections:

  • Multi-DID method support (Section 5.6): Pluggable resolution of did:aicp, did:key, and did:web via the Strategy pattern. New methods can be registered without modifying existing code.
  • Capability-based access control (Section 5.7): Fine-grained, object-capability-style permissions with hierarchical wildcard matching and resource-scoped grants.
  • OpenID Connect bridge (Section 5.8): AICP DIDs mapped to OIDC-compatible ID tokens with standard discovery and JWKS endpoints.
  • Federated ANS (Section 6.4): Three-tier resolution (local, domain, federated peers) with parallel peer queries and DID-based deduplication.
  • MCP server integration (Section 13.6): Built-in MCP server exposing 16 AICP tools over JSON-RPC 2.0 stdio, enabling any MCP-compatible AI agent to use AICP.

15.2 Protocol Extensions (Planned)

  • Zero-knowledge proofs: Enable agents to prove credential attributes (e.g., "spending limit exceeds $1000") without revealing exact values, enhancing privacy.
  • Cross-chain payment bridges: Extend the payment adapter framework to support Ethereum, Solana, and other L1/L2 chains beyond USDC.
  • did:ion / did:peer support: Add resolvers for additional DID methods as the ecosystem matures.
  • Selective disclosure: Enable agents to share only specific credential attributes during onboarding, minimizing data exposure.
  • Delegated sub-agents: Allow agents to delegate a subset of their capabilities to sub-agents, enabling hierarchical agent topologies.

15.3 Ecosystem Integration (Planned)

  • A2A bridge: AICP credential verification as an A2A service, allowing A2A agents to verify identities through AICP.
  • Agent framework adapters: Native integration with LangChain, AutoGPT, CrewAI, and other agent frameworks.
  • OIDC relying party mode: Accept external OIDC tokens (Google, Azure AD) and map them to AICP principal DIDs, enabling enterprise SSO integration.
  • Verifiable Presentations: Support W3C Verifiable Presentations for composing credentials from multiple issuers into a single proof.

15.4 Governance

  • Consortium governance model: Define formal governance for validator admission, protocol upgrades, and dispute resolution.
  • Economic model: Design sustainable economics for AICP node operators and service providers.
  • Standards body engagement: Pursue formal standardization through W3C, IETF, or a dedicated AICP Foundation.

16. Conclusion

The Agentic Identity and Commerce Protocol addresses the foundational infrastructure gap in the autonomous AI agent ecosystem. By providing cryptographic identity anchored to human accountability, decentralized service discovery, standardized onboarding, and provider-agnostic payment capabilities, AICP enables agents to operate autonomously while maintaining security, auditability, and trust.

AICP's four-layer architecture — Identity, Discovery, Onboarding, and Commerce — is deliberately complementary to existing agent protocols. It provides the "plumbing" that MCP, A2A, and ACP assume exists but do not implement. An agent equipped with AICP can discover services it has never seen, prove its identity and authorization, negotiate terms, pay for access, and begin operating — all without human intervention and all within delegated boundaries.

The reference implementation demonstrates that this vision is not theoretical. A production-grade Go server with PostgreSQL storage, Redis caching, consortium consensus, and comprehensive observability is deployable today. Client SDKs in TypeScript and Python reduce the "five-call experience" to a few lines of code. The Kubernetes operator automates consortium lifecycle management. Recent additions — multi-DID resolution, federated ANS, capability-based access control, an OIDC bridge, and a built-in MCP server — further strengthen AICP's interoperability with existing identity systems and agent frameworks.

As the agent economy grows from millions to billions of autonomous transactions, the need for standardized identity and commerce infrastructure will only intensify. AICP is an open invitation to the community — protocol designers, agent framework authors, service providers, and enterprises — to build on this foundation together.

The protocol is open source under the Apache 2.0 license. Contributions, feedback, and collaboration are welcome.
